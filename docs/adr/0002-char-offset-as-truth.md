# ADR-0002：正文唯一真相是字符偏移，分页只是缓存

- 状态：已接受
- 日期：2026-10-31
- 相关：`docs/DEVELOPMENT_PLAN.md` §3.5.3、`packages/reader`、`packages/domain` 的 `ReadingProgress`、`packages/data` 的章节表

## 背景

阅读器要同时支持滚动与分页，还要记住「读到哪」。用「页码 + 章号」记进度最直观，但页码依赖
字号、行距、屏幕尺寸、字体版本 —— 用户换一次字号，所有页码失效，进度会漂移到别的段落。
多端同步时问题更严重：手机与平板的分页必然不同。

## 决策

- 章节以**解码后文本的字符偏移**定位：`startOffset` / `endOffset`，切片即正文。
- 阅读进度存 `(bookId, chapterIndex, charOffset)`，**不存页码作为真相**。
- 分页结果只是缓存：`LayoutSpec.layoutHash`（排版全字段 + 开关位图 + 字体版本）作为键，
  缓存在内存 LRU 与数据库 `page_layouts`（M2 落地），随时可丢、可重建。
- 任何影响行盒的字段漏进 `layoutHash`，都会导致旧页表错位 —— 改 `LayoutSpec` 必须同时改 hash 组成，
  并在 PR 里说明缓存会全量失效。

## 后果

**正面**

- 换字号、换设备、换主题都不丢进度。
- 分页算法可以随时重写，不影响已存数据。
- 同步只需交换很小的进度对象，冲突可仲裁（`revision` 优先）。

**负面**

- 字符偏移对编码敏感：解码方式变了（例如 GBK → UTF-16 改实现），偏移会失效，需要迁移或重新分章。
- 从偏移恢复阅读位置时要重新分页找页，冷启动多一次布局开销（由空闲帧预分页缓解）。
- 富文本格式（EPUB 的 CSS 排版、图片）无法完全用纯字符偏移表达，需要 `ChapterRef.href` 兜底。

## 替代方案

| 方案 | 为什么不选 |
| --- | --- |
| 存页码 | 任何排版变化都让进度失效，多端必然错位 |
| 存百分比 | 精度不足，长章节内会跳段 |
| 存 EPUB CFI | 只适用于 EPUB，TXT 无 CFI，且实现复杂 |

## 复审条件

引入富文本排版（图片、脚注、表格）导致偏移不足以定位时，扩展为 `charOffset + 节点路径` 的复合定位。
