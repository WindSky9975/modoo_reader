# ADR-0004：先滚动后分页的渲染路线

- 状态：已接受
- 日期：2026-10-31
- 相关：`docs/DEVELOPMENT_PLAN.md` §5（M1–M2）、`packages/reader` 的 `TextLayoutEngine`

## 背景

阅读体验的两条主线 —— 滚动与分页 —— 实现成本差异极大。滚动几乎是「把文本放进 ListView」；
分页要做 `TextPainter` 布局、行盒切分、标点挤压、页高对齐、缓存失效、预分页。单人三个月做 MVP，
不可能把两套都打磨到能用。

## 决策

- **M1 只做滚动阅读**，但把分页契约先定下来：`TextLayoutEngine.paginate(PaginationRequest) -> List<PageSpan>`
  放在 `packages/reader`，实现（依赖 `TextPainter`）放 `packages/ui`。
- **M2 接横向分页**，M6 才考虑仿真翻页（ADR-0008）。
- 滚动模式不是临时方案：它要在竖排文本、长章节、超长段落上都达到可发布的完成度。

## 后果

**正面**

- MVP 能在 M3 交付；阅读器的「能读」不依赖分页器完成。
- 分页契约先定，滚动与分页共用同一套章节偏移与进度模型（ADR-0002），后接不返工。
- 滚动模式本身就是「字体渲染出问题」的最短验证路径。

**负面**

- M1–M2 期间产品看起来不如竞品「精致」（分页是很多用户的默认期待）。
- 部分排版优化（避头尾、跨页孤行）在滚动模式下收益小，工作量被推后。
- 两套模式意味着两套性能预算与两套测试。

## 替代方案

| 方案 | 为什么不选 |
| --- | --- |
| 直接做分页 | 分页没打磨好时体验比滚动更差，且阻塞 MVP |
| 只做分页不做滚动 | 长段落与图片内容滚动更自然；且分页实现风险集中 |
| 用 WebView + CSS 多栏分页 | 排版控制力差、性能不可控、与「自研中文排版」目标冲突 |

## 复审条件

M2 分页实测 p95 翻页耗时超过预算（16.7ms）且滚动模式无法达到同等阅读完成度时，重新评估优先级。
