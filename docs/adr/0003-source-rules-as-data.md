# ADR-0003：书源规则作为「数据」由内置引擎执行，不作为插件代码分发

- 状态：已接受
- 日期：2026-10-31
- 相关：`docs/DEVELOPMENT_PLAN.md` §3.7、`packages/source_engine`、ADR-0006

## 背景

「书源」是一组抓取规则：搜索页怎么请求、结果怎么取、目录怎么翻、正文怎么抽。
规则变化很频繁（站点改版），而代码发布很慢 —— 如果每条书源都写成 Dart 插件，用户每次都要等发版。

## 决策

书源是**数据**（JSON `SourceRule`），由内置引擎 `modoo_source_engine` 解释执行。选择器以表达式前缀区分：
`@css:`、`@json:`、`@regex:`、`@js:`。前三种是纯函数解析，`@js:` 需要进沙箱且默认关闭。
规则可通过文件导入/导出，不随 App 发布，也**不由本仓库提供任何具体规则**（ADR-0006）。

## 后果

**正面**

- 站点改版时用户自己改规则即可，不必等发版。
- 规则可分享、可版本化、可 diff，比编译进 App 的代码更轻。
- 引擎升级能一次性修好所有旧规则；只写 Dart 插件则每条规则都要单独改。

**负面**

- JSON DSL 表达力有限，遇到签名、加密、复杂分页要扩展语法或退回 `@js:`。
- `@js:` 是唯一执行用户提供代码的入口，必须自建限制（超时、内存、禁用 I/O），是长期安全负担。
- 规则作者门槛高于「复制一个插件」；调试体验依赖未来的规则调试面板（M6）。

## 替代方案

| 方案 | 为什么不选 |
| --- | --- |
| 每条书源一个 Dart 插件 | 站点改版就要发版，节奏上不可行 |
| 全部交给 `@js:` | 安全边界与可调试性都最差 |
| 只做浏览器扩展式注入 | 与本地优先、离线可用的目标冲突 |

## 复审条件

`@js:` 规则占比超过一半，或引擎无法在不为每条规则打补丁的前提下支持主流站点格式时，考虑引入受限脚本能力。
