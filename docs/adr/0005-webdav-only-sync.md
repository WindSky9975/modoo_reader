# ADR-0005：同步只支持 WebDAV，不自建服务

- 状态：已接受
- 日期：2026-10-31
- 相关：`docs/DEVELOPMENT_PLAN.md` §3.8、`packages/sync`、`packages/plugin_api` 的 `SyncBackend`

## 背景

同步（进度、书签、笔记、设置）需要一个存储与账号体系。三条路线：自建后端、接入网盘（WebDAV）、
只做本地导出/导入。自建后端意味着运维、备案、隐私合规与长期成本；纯本地方案体验割裂。

## 决策

- 同步**只支持 WebDAV**（用户自备 Nextcloud / 坚果云 / Synology 等），不自建服务器、不做账号体系。
- `SyncBackend` 是插件能力接口，但 M5 只实现 WebDAV 一个。
- 冲突裁决：`revision` 大者胜；相同时比 `updatedAt`；仍相同则保留双方（`keepBoth`）并提示用户。
  不信任服务器与客户端时钟。

## 后果

**正面**

- 零运维、零账号、零遥测：数据存在用户自己的网盘里，符合项目隐私立场。
- 没有后端就没有「服务下线导致数据不可用」的风险。
- WebDAV 是成熟协议，客户端实现小（几个 HTTP 方法）。

**负面**

- 用户需要自备网盘并理解 WebDAV 配置，门槛高于「扫码登录」。
- 没有服务端，就无法做实时同步、多人协作、服务端检索。
- 网盘的并发语义弱（多数不支持原子 compare-and-swap），只能靠 `ifMatchEtag` 与冲突裁决兜底。

## 替代方案

| 方案 | 为什么不选 |
| --- | --- |
| 自建后端 | 运维与合规成本远超单人项目承受范围 |
| 各家网盘 SDK 直连（百度/OneDrive/iCloud） | 每家都要 OAuth 与审核，维护成本高，且部分要求上架 |
| 只做本地导出/导入 | 体验割裂，跨设备几乎不可用 |

## 复审条件

WebDAV 用户占比低且「配置太难」成为主要流失原因时，考虑增加一个端到端加密的托管方案
（必须默认关闭、可自托管，且写新 ADR）。
